# Shop rules

`shop-rules.yaml` is the shop's processing knowledge written so the designer — code or AI — can use
it. It started as *Cabinet Job Processing Checklist 2026.docx*, which was written for processing
jobs in Cabinet Vision. This version keeps **what the shop builds and why**, and drops **how to click
through Cabinet Vision to get it** (list at the bottom).

It's the seed for AI-LAYER-PLAN Stage F. For now it lives in the repo as a file; later it becomes
per-team data, snapshotted into each revision.

---

## Adding a rule

Copy the block below to the end of the right section and fill it in. Only the first six fields
are required.

```yaml
- id: DRW-011            # next number in that section; never reuse one
  title: Short name
  scope: drawer          # room | wall | run | cabinet | section | face | drawer | part
  kind: check            # check | default | derive | note | sourcing
  owner: code            # code (always the same answer) | ai (needs judgment)
  statement: >
    The rule in plain words, the way you'd explain it to a new hire.
  severity: warn         # checks only: block | warn | info
  styles: [euro]         # leave out if it applies to both
  note: '{width}" MR up {distance}" oc'   # report wording; {braces} filled from the design
  example: '3 5/8" MR up 31 1/2" oc'     # a filled-in sample, never copied as-is
  values: { some_size: '1 1/2' }
  needs: [purpose]       # data the designer doesn't have yet
```

When you aren't sure how to classify one, write the `statement` well and guess the rest — the
statement is what matters. Mark it `status: question` if it's unsettled.

## How the fields get used

- **`owner: code`** — the answer is always the same, so it belongs in the designer's model:
  defaults become settings, derives become calculations, checks become warnings in the panel.
  AI never decides these; it can only see whether they were followed.
- **`owner: ai`** — needs judgment about the whole room (clearances, whether a bookcase frame looks
  proportional). AI reviews the resolved room against these and reports findings.
- **`note`** is the vocabulary the shop and vendors already read. Reports generated by the designer
  should keep using it. Text in `{braces}` is filled in from the design; a list means one of those
  options; a note with no braces is always literal. **`example`** is only an illustration.
- **`needs`** says what the designer can't see yet. A rule with `needs` can't be checked until that
  data exists; a rule without it can be checked against today's model.

## What the checklist says about the plan

**63 of 71 rules are `owner: code`.** Most of the checklist is construction logic with one right
answer, not judgment. That's good news: it shrinks what AI has to be trusted with, and it means
PLATFORM-PLAN Phase 5 (construction rules per team) carries more of the load than the AI layer does.
AI's job is mostly the eight `ai` rules plus finding things **no** rule covers.

**Only about a dozen rules can be checked against today's model** — reveals, deck height, fillers,
end panels, blind corners, drawer stabilizers. The rest wait on data the designer doesn't record yet:

| Missing data | Rules waiting on it | Where it comes from |
|---|---:|---|
| `purpose` (sink, oven, trash, hamper, file, charging, pencil, flipper, bookcase) | 14 | Stage D intent vocabulary — this list should seed it |
| `interior` (fixed shelves, partitions, adjustable shelves, line bore, sections) | 14 | Not planned yet — needs its own plan after cells |
| `drawer_boxes` (box depth, height, slides) | 10 | Derivable from faces + depth once slide rules exist |
| `door_style` (5-piece / slab / glass / mesh, stile and rail widths) | 9 | Option family (PLATFORM-PLAN §3) |
| `materials` | 6 | Room settings + option families |
| `appliances`, `hardware`, `part_shape`, `scribe`, `wood_top` | 2–4 each | Option families / later steps |

Two direct inputs to upcoming work:

1. **Stage D's purpose list** should include `trash`, `hamper`, `file`, `charging`, `pencil`,
   `flipper`, `bookcase` and `closet` alongside `sink`, `dw`, `range`, `fridge`, `oven`, `micro`,
   `hood` — each drives at least one rule here.
2. **Interior** (sections between fixed shelves, partitions, shelf counts) is the biggest gap that
   isn't on any plan yet. It fits naturally under cells: a section is a vertical slice of a cell's
   interior.

## Open questions

Things the checklist leaves unclear or that conflict with the designer as built. Answer these and
update the rule (or drop `status: question`).

1. **DRW-009 roll-out trash.** Some cabinet sizes aren't covered: 24" deep and wider than 24";
   deeper than 24" but under 26". And "24" wide" — does that mean 24" deep *and* exactly 24" wide?
2. **SRC-003 folded fillers at least 7" wide** vs. blind corner fillers ordered ~6" wide. Does the
   7" minimum apply only to Alpha slab fillers that get cut and folded into an L?
3. **INT-001 "nosing on shelves"** as the alternative to a partition over 36" — always acceptable,
   or only for certain materials or depths?

## Left out: Cabinet Vision procedure

These were instructions for operating Cabinet Vision, not rules about the cabinets. They're kept here
so nothing from the original is lost, but the designer shouldn't copy them.

- Adding cabinet notes (right-click → Comments) and sub-assembly notes (Reports → Order Entry).
- Marking Face Frame "Y"/"N" in Room Notes — kept as the `face_frame` room setting instead.
- Drawer Guide Schedules ending in "No Notch", and matching Construction → Drawer Box/Roll Outs
  ("FFI Blum No Dovetail", "FFI Accuride No Dovetail", the pre-finished maple schedules). The
  underlying rules — slide type and the 1/16" wider maple drawers — are kept as DRW-001 and DRW-007.
- Adding drawer notes on the "drw box sub-front", and checking the ProBox report for them.
- Choosing "SLAB – MDF CORE" as the door style in Room Properties for Alpha slab parts, and
  selecting "Get from Alpha" on a part's attribute. The sourcing itself is SRC-001.
- "Anything named End Panel has its width and depth reversed on Cabinet Vision reports."
- Cabinet name keywords (NOCO, NOSIZE, …) — kept as `report_flags`, to become a per-part setting.
- Hinge side, hinge bore and the rest of the section notes were typed as free text in Cabinet
  Vision; they're kept as rules because the designer should produce that text from data.
